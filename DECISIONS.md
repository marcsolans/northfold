# Decisions

Technical decisions not fixed by the specification. Simplest option that satisfies the principles.
Format: **D-NNN — title.** Decision. *Why.*

## Foundations

**D-001 — Engine fork placement.** The complete upstream engine repository (Python framework, Zig CLI, Rust TUI, docs, examples, benchmarks, scripts) is copied into `packages/messer-core/` as one unit. The upstream project, tag (`v2.7.39`) and exact commit (`45f3298899f32f861f8573c918ae22bdf90e489f`) are recorded in `NOTICE` and `LICENSE_REVIEW.md` (the brand name may appear only in those files). *Keeping the tree intact makes future upstream syncs a mechanical rename + diff.*

**D-002 — Package names.** Engine distribution `messer-core`, import name `messer` (`from messer import Agent, Workflow`). Platform packages: `messer_common` (shared kernel), `messer_api` (control plane), `messer_runtime`, `messer_worker`, `messer_scheduler`, `messer_voice`, `messer_mcp`, `messer_connectors`, `messer_sdk`.

**D-003 — Engine dependency pins.** The root `pyproject.toml` pins every package in the upstream lock file through `[tool.uv] constraint-dependencies`. Resolving freely pulled `anthropic` 1.x and `openai` 3.x, which broke 68 engine tests (collector usage accounting). Platform-only dependencies resolve freely. *The engine test suite (5,352 tests) must stay green after the rename.*

**D-004 — Engine platform hooks redirected to Messer.** The engine's "platform" HTTP calls now target the Messer API: `orgs/{org}/apps/{app}/runs/{run}` → `orgs/{org}/projects/{project}/runs/{run}`; `orgs/{org}/k2/{kb}/query` → `orgs/{org}/knowledge-bases/{kb}/query`; `orgs/{org}/integrations/{id}` → `orgs/{org}/connections/{id}/credentials`. `MESSER_API_HOST` may be a full base URL (`http://runtime:8100/internal/v1`), defaulting to `${MESSER_API_URL}/api/v1`. Deployed environments resolve through the runtime (`${MESSER_RUNTIME_URL}/envs/{env_id}`). All upstream hostnames were rewritten to the non-routable `*.messer.local` so no default ever reaches a third party.

**D-005 — Extra shared package.** `packages/messer-common` holds settings, ORM models, sessions/RLS, crypto, pricing, model config, email/storage/queue/event adapters and test fixtures. It is used by the API (control plane) and by the runtime/worker (data plane), which keeps the runtime free of any dependency on control-plane code.

**D-006 — One migrations path: Alembic.** `infra/migrations` (owner connection). Supabase migrations are not used.

**D-007 — Row Level Security model.** Three Postgres roles: `messer` (owner; migrations and *system* work such as webhooks and schedulers, always filtering by `org_id` explicitly), `messer_app` (NOBYPASSRLS; every user request), `messer_readonly` (SQL console and agent SQL, switched per query to a per-knowledge-base reader role). Each request runs in a transaction that sets `app.user_id`, `app.org_id`, `app.superadmin` with `set_config(..., true)`; policies call `messer.has_role(org_id, min_role)` (SECURITY DEFINER over `memberships`). Every business table has `org_id`; policies are generated from a registry in the models and frozen into each migration. `audit_log` is insert-only (UPDATE/DELETE revoked). Auth internals have RLS enabled with no policy (invisible to the app role).

**D-008 — Authentication.** Default local backend: Argon2id passwords, rotating refresh-token sessions (only hashes stored), HS256 access JWTs with Supabase-compatible claims (`sub`, `email`, `aud=authenticated`, `aal`). When `SUPABASE_URL`/`SUPABASE_ANON_KEY` are set, credentials are delegated to Supabase Auth (GoTrue) and its tokens go into the same cookies; user ids equal the Supabase uid. MFA (TOTP + recovery codes) is enforced by Messer in both modes. Social login without Supabase uses OAuth 2.0 code + PKCE directly against Google/Microsoft.

**D-009 — Same-origin API.** The browser calls `/api/v1/*` on the web origin; Next.js rewrites to the API service. Cookies (`messer_at`, `messer_rt`, `messer_org`) are httpOnly/SameSite=Lax on the web domain, so Vercel ↔ Railway needs no cross-site cookies or permissive CORS.

**D-010 — Frontend toolchain.** Next.js 16 (App Router, `proxy.ts`), React 19, TypeScript 6.0 (the native TypeScript 7 compiler is not yet a safe default for Next), Tailwind CSS 4, Radix primitives with shadcn-style components written in `packages/ui` (the shadcn registry is not fetched at build time), Geist fonts from npm (no Google Fonts request at build or run time).

**D-011 — Internationalisation.** next-intl without locale URL prefixes. Spanish is the default for everyone; English is opt-in (language switcher, profile, or `?lang=en`) and persisted in `NEXT_LOCALE`. Messages are split per namespace (`messages/<locale>/<namespace>.json`) so each area owns its file.

**D-012 — Content Security Policy.** Nonce-based strict CSP (`'strict-dynamic'`) set per request in `proxy.ts`; Monaco is served from `/monaco/vs` (copied from npm at install) instead of a CDN. `/embed/*` pages may be framed (embeddable chat); everything else sends `frame-ancestors 'none'`.

**D-013 — Model configuration.** `packages/messer-common/src/messer_common/config/models.yaml` holds tiers (Fast = `anthropic/claude-haiku-5-5`, Standard = `anthropic/claude-sonnet-5-5`, Powerful = `anthropic/claude-opus-5-5`), Guard small/large models, Composer roles, Bedrock EU model ids (`anthropic.<id>`, Mantle client, `eu-central-1`) and seed prices for `model_prices`. Haiku 5.5 cache read/write prices are derived (0.1× / 1.25× input) because the cached models table publishes input/output only; they are editable in /admin.

**D-014 — Logo.** A red square (`#D52B1E`) with a white diagonal blade and the wordmark. The Swiss cross was avoided: it is a protected national emblem.

**D-015 — Test isolation.** Python tests use a real Postgres database (`$MESSER_TEST_DATABASE`, default `messer_test`) migrated once per session and truncated after each test, and Redis db 15. Parallel workstreams use different database names.

**D-016 — Email locally.** SMTP to Mailpit (`:1025`, UI `:8025`). In `local`/`test`, if SMTP is unreachable the email is logged to the console instead of failing the request. E2E tests read emails through the Mailpit API.

**D-017 — Docker in the build environment.** The build sandbox has no Docker daemon, so `docker compose up` cannot be executed here; compose files are validated with `docker compose config` and every service is also runnable natively (`make api`, `make web`, …). CI runs the same services natively.

**D-018 — Runtime topology.** The control plane never executes project code. `services/runtime` (data plane) receives run requests with a service token, fetches the project's code at an exact git commit as a tar.gz from the API (`/internal/v1/projects/{id}/archive`, cached immutably per commit), and runs it in a per-(project, commit) sandbox process. Engine platform calls from the sandbox (tracing GET/PATCH, model proxy, tool proxy, knowledge, connector actions, file persistence) go to the runtime's own `/internal/v1` with a signed sandbox token scoped to org/project/commit. A new commit gets a new sandbox, so deploying never interrupts in-flight runs.

**D-019 — Model gateway.** Every model call (agents in sandboxes and platform features via `messer_common.llm.complete`) goes through the runtime's Anthropic-compatible `/internal/v1/orgs/{org}/proxies/anthropic/v1/messages`. It applies the org's model policy, checks credits, plan limits and hard-stop budgets (5 s cache), routes `eu_strict` organizations to Bedrock EU only, otherwise Anthropic first with Bedrock as fallback on 429/5xx/529, records per-call usage and cost in Redis keyed by run id, and the run is charged once at the end (`credits.charge_usage`, idempotent per run). Project secrets named like provider credentials (`ANTHROPIC_*`, `AWS_*`) are never passed to sandboxes, so agent code cannot bypass the gateway; other providers' keys (OpenAI, …) are bring-your-own and not charged.

**D-020 — Offline demo model.** Without `ANTHROPIC_API_KEY`/AWS credentials the gateway serves `messer/demo`: a deterministic Anthropic-format responder that selects tools by keyword, fills arguments from the message (emails, ids, amounts, quoted text), summarizes tool results and labels itself. Runs are marked `demo` and cost 0, so every flow (approvals, traces, credits) works end to end without keys.

**D-021 — Sandbox isolation.** Today: one OS process per (project, commit) started with a scrubbed environment (only safe variables, the project's own secrets, the sandbox token), its own session, `RLIMIT_AS` (default 2 GB), `RLIMIT_CPU`, `RLIMIT_NOFILE`, per-run wall-clock timeout, idle reaping after 15 minutes, Unix-socket transport (no TCP port). Moving to stronger isolation only replaces `SandboxPool._spawn`: **gVisor** — run the runtime image with `runtimeClassName: gvisor` (no code change) or spawn each sandbox with `runsc`; **Firecracker** — boot a microVM per sandbox from a rootfs with the engine preinstalled and forward the same Unix-socket protocol over vsock; **E2B** — create a sandbox per (project, commit), upload the archive, start `python -m messer_runtime.sandbox.server` and proxy the socket through E2B's process API. The sandbox protocol (HTTP over a socket: `/members/{name}/stream|evals|flow|schema`) stays the same in all three.

**D-022 — Run identity and memory.** Run ids are the engine's UUIDv7 strings stored as UUIDs; `runs.trace` keeps the full engine trace (list of span records) so conversations continue with `parent_run_id` (memory) and paused runs resume with `resume={approval_id: resolution}` on the same commit. Spans are flattened into `spans` with kind (agent/workflow/step/llm/tool/guardrail), tokens and cost. Studio, API (`session_id`) and channel conversations map to `conversations.last_run_id`.

**D-023 — Approvals.** An approval row is created for each engine APPROVAL event of a paused run; the run resumes when every approval of it is decided (approve, deny, approve with changes → engine `override_input`). Approvers need at least the role configured on the tool. Writes happen on the owner connection after an RLS-scoped read and role check (approvers may be viewers). Email links are signed per recipient and decision, and opening them never decides (a confirmation page POSTs), so link scanners cannot approve; links are single-use because a decision can only be recorded once. Expired approvals get their default action (`expiry_action`, default deny) from the scheduler.

**D-024 — Triggers.** Cron (5-field, IANA time zone, minimum one minute, evaluated by the scheduler with row locks), signed webhooks (`X-Messer-Signature: t=<unix>,v1=<hmac-sha256(secret, "t.body")>`, 5-minute tolerance, secret shown once), inbound email (one `wf-<token>@MESSER_INBOUND_EMAIL_DOMAIN` address per trigger; provider webhook `/api/inbound/email`, Postmark format supported; a simulate endpoint for local/demo use), knowledge-base file uploads and connector events (`messer_common.triggers.emit`). Every firing is a worker job whose id is derived from the event id (duplicates collapse), and the run id is derived from (trigger, event) too. Workflows receive `{"event": payload, **static_input}`; agents receive a prompt built from the payload. Production triggers run the deployed version; development triggers run HEAD.

**D-025 — Public run API.** `/v1/projects/{id}/workforce/{name}/run|stream` and `/v1/runs/{id}` accept API keys (`runs:write` / `runs:read`) or a session. The default environment is production (the deployed version; 409 `not_deployed` otherwise); `environment=development` runs the latest commit.

**D-026 — Billing modes.** With Stripe keys, billing uses Stripe Checkout, the customer portal, Stripe Tax and webhooks (idempotent per event id; state machine trial → active → past_due → grace → canceled/read-only). Without keys a simulated provider with the same state machine and a test checkout page runs end to end (test mode). Upgrades within a period grant only the credit difference; at most one automatic top-up every 10 minutes and five per day (`messer_common.credits.maybe_auto_topup`, executed by the worker job `auto_topup`, re-checked by the scheduler). Plan limits are not enforced for organizations without a plan (system-created ones only). Impersonation sessions last at most 2 hours, never target superadmins and are audited with an `imp` token claim.

**D-027 — Studio chat transport.** The playground is built on Messer's own SSE events (engine events plus RUN_STARTED/RUN_FINISHED/APPROVAL) instead of a generic chat kit, because it renders inline approval cards that continue the same stream, tool cards with input/output, guardrail notices and per-run cost. Model selection shows tiers and explicit models from `GET /api/v1/models` (prices, EU availability, org policy).

**D-028 — Document parsing.** Knowledge ingestion parses PDF (PyMuPDF), DOCX, PPTX, XLSX/CSV, HTML, Markdown/TXT and EML natively with structure-aware chunking. Docling is an optional adapter used only when installed: it requires PyTorch, whose dependency pins conflict with the engine's. Embeddings: local `intfloat/multilingual-e5-small` (fastembed, downloaded once into the runtime cache), Voyage or Bedrock when keys exist, and a deterministic hash embedder offline/tests.

**D-029 — Verified domains for SSO and SCIM.** Users are global accounts, so an organization could otherwise claim another company's addresses. SSO login, "enforce SSO" and SCIM account creation require an email domain verified by DNS TXT (`org_domains`). SSO-mapped roles never grant `owner`.

**D-030 — Audit entries under RLS.** `audit.record` sets id and timestamp client-side so inserts need no `RETURNING`; the audit log stays readable only by admins while any role can append its own entries.

**D-031 — GitHub sync.** A project connects to `owner/repo@branch` through a GitHub App installation (installation tokens from an RS256 App JWT) or, without App keys, an admin's fine-grained token stored encrypted. Every Messer commit triggers a debounced push (never forced); a push webhook triggers fetch + merge into the project repo, where Messer's side wins only on true conflicts and the merge commit lists them. Changed members are re-parsed (code wins when the config cannot be derived) and versioned with `source="github"`. Credentials travel as git HTTP headers via environment variables, never in URLs or arguments; incoming symlinks, submodules and files over 25 MB are refused.

**D-032 — Self-contained export.** `export.zip` contains the project at a ref, the project's knowledge (chunks JSONL, tables as CSV + schema, exported through the agent's policy view, so restricted data stays restricted), the engine wheel, a Dockerfile and a `docker compose` file: one container per workforce member (`python -m messer.server`) plus `messer.platform.standalone`, a small local implementation of the platform endpoints (keyword BM25 knowledge search, read-only SQL on SQLite, email via SMTP or log, files on disk, JSONL traces, Anthropic pass-through or a labelled offline model, connectors reported as unavailable). Secret values are never exported, only their names in `.env.example`.
